## 🔴 The stock data is unusable — do not migrate it

| Stock on hand | Products |
|---|---|
| Negative | **187** |
| Zero | 19 |
| Positive | **0** |

Not one product has a positive quantity. Aronium's stock was never initialised, so
every sale decremented from zero and drove the count negative — `Ciel 1Lt` reads −164,
`Cheetos Flamin'Hot` −97. The `Stock.Control.NegativeQuantity` permission was granted at
level 0, so nothing ever stopped it.

**Consequence:** opening stock has to come from a **physical count**, not from the old
system. There is no shortcut and no partial rescue — the numbers carry no information.

This is an argument *for* the phasing already chosen: build the catalogue first, then
count real stock into it. The count is unavoidable work; doing it early means the new
system starts truthful.

## 🟠 Half the catalogue has no cost price

**99 of 206 products** have no cost recorded — and it is worst exactly where it hurts:

| Price | Product |
|---|---|
| $250.00 | Salvavidas Toldo |
| $200.00 | Salvavidas Andadera Animal |
| $200.00 | sandalia de niño |
| $150.00 | Salvavidas con Agarradera |
| $150.00 | Salvavidas Andadera Vehiculos |
| $120.00 | Salvavidas Grande |

The high-value items — life vests and sandals — are the ones missing cost, so margin
reporting is blind precisely on the products where margin matters most. Snacks and
sodas, where the peso value is small, are the ones with cost filled in.

Cost is not needed to *sell*. It is needed to know whether the season made money.
Worth filling in before March; not a blocker for the till.

## ✅ Better than expected

**Every checkable barcode has a valid check digit.** 226 of 231 verified; the other 5
are EAN-8, now also validated after the importer was extended.

| Length | Count | Symbology |
|---|---|---|
| 13 | 197 | EAN-13 |
| 12 | 29 | UPC-A |
| 8 | 5 | EAN-8 |

**The till must handle all three lengths.** UPC-A is EAN-13 with a leading zero; treat
them as the same code or imported stock silently fails to match.

**No duplicate barcodes** — no code points at two products.

**Internal codes are already in use.** 20 products carry prefix-`2` codes in the
`23033119…` range (Panales para Agua, Papel Higienico, the medicines, Corona Light Six
Pack). So the in-store range convention is already established here — the generator
should extend that series rather than start a competing one.

## 📋 Design consequences

**6 products still need generated codes:** Churrumais 70gr, Fuzetea Limon 600ml,
pistola de agua chica, cafe, sandalia de niño, Pistola de agua mediana.

**34 groups is too many for a till button grid.** The existing groups mix brands
(`Sabritas`, `Doritos`, `Ruffles`, `Gamesa`, `Emperador`, `Chokis`) with categories
(`Desechable`, `Dulces`, `Medicamentos`, `Salvavidas`). A cashier hunting for Cheetos
should not have to know whether it filed under a brand or a category. Consider a
consolidated top level for the till — Botanas, Refrescos, Cerveza, Dulces, Desechables,
Salvavidas, Medicamentos, Otros — with the brand groups kept underneath for admin.

**`MeasurementUnit` should not be carried over.** It is free text with ~80 inconsistent
spellings: `600 ml` vs `600ml`, `105 gr` vs `105gr`, `2.5 Lt` vs `2.5Lt`, `1pc` vs
`1 pc` vs `1pcs`. 53 products have none at all. Size already lives in the product name
(`Coca-Cola Original 2lt`), which is where a cashier reads it. Preserved as
`legacy_unit` for reference; never authoritative.

**13 products were never sold** in four years. Candidates for retirement — but review
before deleting, since some may be seasonal stock that simply had no sale recorded.
